### 0. 开场（约 40 秒）

各位老师、同学好，我是王旭帆。这次 Agent 基础实验，我做的事情是：读 ReAct 论文，然后不用 LangChain，从零手写一个本地 Agent，让它能调用真实 API 完成天气查询。

我想先给一个结论：

> **Agent 的关键不只是模型，而是模型外面那圈循环。这个实验就是把那圈循环拆开，看看它到底怎么跑起来。**

---

### 1. ReAct 论文（约 1 分 20 秒）

ReAct 的核心是让模型交替做两件事：推理和行动。

它每一步先生成 **Thought**，也就是“我现在要干什么”；然后生成 **Action**，比如调用天气工具；环境执行后返回 **Observation**，也就是真实结果；Observation 再进入下一轮 Thought，直到模型给出 **Final Answer**。

它和 CoT 的区别是：CoT 只有推理，没有外部反馈，所以拿不到实时信息；Act-only 只有动作，没有高层规划，容易乱调工具。ReAct 把两者结合起来：**推理指导动作，观察修正推理**。

对应到我的实现，就是四个问题：

1. **协议**：模型怎么表达工具调用？
2. **执行**：本地代码怎么校验和运行？
3. **回填**：结果怎么变成模型能读懂的 Observation？
4. **收口**：格式错误、重复调用、无限循环时怎么停？

---

### 2. 系统设计（约 1 分 30 秒）

（切图1）

整体架构分五块：DeepSeek 作为策略模型，ReAct 循环在 `agent.py`，工具注册表在 `tools.py`，外部 API 包括 Open-Meteo 天气、必应搜索和网页抓取，交互层是 CLI 和本地 Web。

（切图6）

工具接入我做成最小协议：**一个普通函数、一份 JSON Schema、一次注册**。`describe_tools()` 把 schema 拼成文本注入 system prompt；模型输出 Action 后，统一走 `run_tool`，做参数校验、类型转换、异常捕获和结果截断。

工具函数的约定是：**只返回字符串，失败就抛异常，不控制循环**。这样任何工具错误都会变成一条模型能读懂的 Observation。

（切循环代码）

循环里还有几个保护：

- 完全相同的工具和参数只执行一次；
- 连续格式错误提前收口；
- 最多 8 步；
- 每次调用前后检查取消信号；
- `stop=["Observation:"]` 强制模型在写完 Action 后停下，避免它自己编造工具结果。

### 3. 实验结果（约 2 分 20 秒）

（切图8）

先看对照实验。同一个问题“北京今天天气怎么样”，直接问 DeepSeek，它回答：

> “抱歉，我无法实时获取天气信息。建议你打开天气App或搜索‘北京天气’查看最新情况。”

1 次调用，42 tokens，任务没有完成。

然后交给 ReAct Agent。它第一轮 Thought 是“需要查实时天气”，Action 调用 `get_weather`，Observation 拿到 15.3°C、大部晴朗、今日降水概率 100%。第二轮它判断信息足够，给出 Final Answer：现在适合出门，但记得带伞、早晚添衣。2 次调用，8135 tokens。

这里 token 开销高了，但换来的是实时依据。**ReAct 不是更省，而是能完成 Direct LLM 完成不了的任务。**

（切多工具表）

再做一个组合任务：查天气、整理简报并保存到文件。Agent 用了 4 轮，依次调用 `get_weather`、`write_file`，最后给出总结。这说明工具可以组合，模型不需要预先知道固定流程，而是根据每一步的 Observation 决定下一步。（这个任务最初还调用了空气质量工具；该工具后来在精简动作空间时移出，只保留内部实现。）

（切测试图）

最后是自动化测试：159 个离线用例，158 通过，1 个符号链接用例因为 Windows 权限跳过。覆盖解析、循环、工具安全、文件与命令、Git 与测试、自进化裁判、记忆、会话、SSE、位置授权与工具授权等。

---

### 4. 分析（约 1 分 10 秒）

为什么 ReAct 有效？我总结四点：

1. **接地**：实时信息来自工具；
2. **可观察**：Thought / Action / Observation 每一步都能看；
3. **能恢复错误**：工具异常会变成 Observation，模型可以换参数或换工具；
4. **可组合**：新增工具不用改循环。

但它也有代价和风险：token 和延迟更高；模型可能不按格式输出；可能重复调用；可能选错工具；外部 API 可能失败。所以工程上必须有解析器、最大步数、重复拦截、异常转 Observation。

边界也要说清楚：这是**机制复现**，不是论文指标复现；没有 benchmark；15 个工具比论文的动作空间大，工具选择本身是混淆变量；模型仍然是云端 API，不是本地权重；“本地”指的是循环、工具和 Web 服务在本机。新增的文件读写和命令执行默认访问本机任意路径，靠分级授权（默认 `auto`）约束，不是权限沙箱。

---

### 5. 结论（约 40 秒）

最后用一句话总结：

> **ReAct 不是一个模型能力，而是一套工程循环。模型负责决定下一步，真正的能力来自工具、观测和约束。**

这次实验让我最大的收获是：Prompt 格式就是协议，Observation 就是接口，错误处理不是附加功能，而是 Agent 能稳定运行的前提。

## 可能被问到的问题

### 1. 为什么不用 LangChain？

因为这次的目标是理解 Agent 的最小闭环。用框架会把循环、解析、工具执行都封装掉；手写一遍，才能说清楚每一层在做什么。

### 2. 为什么不用 function calling？

有两个原因：一是文本协议更接近 ReAct 论文的原始设定，能看清“模型输出 → 解析 → 执行 → Observation”的全过程；二是方便换模型。function calling 是另一种 Action 接口，不是替代 Agent 循环。后面可以加一个适配器做对照。

### 3. 天气 API 是什么？需要 Key 吗？

Open-Meteo 的公开天气 API，不需要 Key；空气质量函数仍保留在内部库中，但当前不注册给模型。地理编码也是 Open-Meteo，失败会回退到其他公开服务。

### 4. 模型不按格式输出怎么办？

解析器会兼容全角冒号、代码围栏和裸参数；解析失败会把格式提醒作为 Observation 喂回去；连续错误达到上限就提前收口；还有 `stop` 序列防止模型自己编造 Observation。

### 5. 15 个工具是不是太多了？

已经从 26 个精简到 15 个，但仍然偏多。工具越多，工具选择越难，评测时会把动作空间收敛到最小集合，避免工具选择成为混淆变量。文件与命令工具还扩大了风险面，所以提供 `ask`/`edits`/`auto`/`readonly` 分级授权，默认在项目内自动放行、项目外确认并拒绝明显危险命令。

### 6. 成本和延迟怎么样？

ReAct 明显更高：天气任务 2 次模型调用、8135 tokens；Direct 只有 1 次、42 tokens。它适合“必须获取外部信息”的任务，不适合所有问题都走多轮。

### 7. 这算真正的 Agent 吗？

按 ReAct 的定义，算基础版：有循环、工具、观测和最终答案。但没有多 Agent、长期规划和反思，这些是下一步。

### 8. 记忆系统呢？

项目里还实现了五层记忆：scratchpad、历史摘要、会话记忆、全局记忆、向量索引。本实验的重点是 ReAct 主循环，记忆是扩展能力，报告里有单独拆解。

## 如果只有 3 分钟

只讲三件事：

1. **ReAct 四步**：Thought → Action → Observation → Final Answer；

3. **一句边界**：这是机制复现，不是指标复现；ReAct 的代价是更多 token 和更复杂的工程约束。
